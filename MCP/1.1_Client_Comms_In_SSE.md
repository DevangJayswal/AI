In Server-Sent Events, since communication is unidirectional from server to client, clients must use **separate HTTP requests** outside the SSE stream to communicate their intentions back to the server. This creates a hybrid communication pattern where SSE handles real-time updates while traditional HTTP methods handle client-initiated actions.

## Standard HTTP Requests for Client Communication

The most common approach is using regular REST API calls alongside SSE connections. Clients send POST, PUT, or DELETE requests to specific endpoints to communicate their intentions[4].

```javascript
// SSE connection for receiving updates
const source = new EventSource('/events');
source.onmessage = function(event) {
    console.log('Received:', event.data);
};

// Separate HTTP request to communicate intention
fetch('/api/broadcast', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ message: 'Hello from client' })
});
```

For example, in a chat application, clients would maintain an SSE connection to receive new messages while sending their own messages through POST requests to a separate endpoint[4].

## Event-Driven Architecture Patterns

Many applications implement an **event-driven pattern** where client actions trigger server-side events that are then broadcast to all connected SSE clients. The server acts as a message broker, receiving client intentions via HTTP requests and distributing the results via SSE streams[7].

**Typical workflow:**
1. Client sends HTTP POST request with action data
2. Server processes the request and updates application state
3. Server broadcasts the state change to all SSE subscribers
4. All connected clients receive the update in real-time

## Subscription Management

Clients can communicate subscription preferences through query parameters or headers when establishing the SSE connection[6]:

```javascript
// Subscribe to specific event types
const source = new EventSource('/events?filter=notifications&userId=123');

// Or use different endpoints for different event streams
const stockSource = new EventSource('/stocks/AAPL');
const newsSource = new EventSource('/news/technology');
```

## Hybrid Communication Examples

**Real-time dashboard scenario:**
- SSE stream delivers live metrics and alerts
- Client sends configuration changes via PUT requests
- Server broadcasts updated configurations to all dashboards

**Live chat application:**
- SSE delivers incoming messages to all participants
- Clients send new messages via POST requests
- Server broadcasts new messages through SSE to all connected users

**Stock trading platform:**
- SSE streams real-time price updates
- Clients place orders through POST requests to trading endpoints
- Server confirms trades and broadcasts market updates via SSE

This separation of concerns allows applications to leverage SSE's efficiency for real-time updates while maintaining the reliability and simplicity of HTTP requests for client-initiated actions. The key is designing your API endpoints to work harmoniously - using SSE for server-to-client data flow and REST APIs for client-to-server communication.
